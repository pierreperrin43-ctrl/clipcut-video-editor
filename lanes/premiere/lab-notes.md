## Every step

- **The lane = the `premiere-pro` skill driving the pinned `vendor/premiere-mcp/` engine (v1.2.3) through the CEP bridge panel**, or headless via `lanes/premiere/premiere-bridge.mjs` (`replay` / `zoom` / `frame` / `grade-layer`, no MCP session needed). Graphics on the timeline validated 2026-07-18; AME banned (exportAsMediaDirect via ES if a bounce is truly needed); `zoom` takes `at` (sequence time) or `offset` (frames) and clears only from the ramp start. Read-back-after-write, always. Wiring and pin: the skill.
- **The bridge has ONE output contract: one line out, `ERROR:` in, a 65535-char return cap, and a timeout you pass (2026-09-19).** `node lanes/premiere/premiere-bridge.mjs es (--job projects/<job> | --no-guard) '<script>'` is the sanctioned runner for ad-hoc ExtendScript and owns all four; `lanes/premiere/pes.py` is the Python side of it (`es(script, timeout=None, job=None)` — pass `job` to run the guard on THAT call — plus `paged(make_script, size=40)` for a readback that would hit the cap), and a lane script imports it rather than growing its own parser. It wraps the caller's script in a try/catch, so a runtime failure comes back as `ERROR: <message> @ line <n>` instead of the bare "ExtendScript execution failed via CEP evalScript()" that costs two dead round-trips to localize. It prints EXACTLY one line — the result verbatim, or single-line JSON for an object; that `ERROR:` line comes back on STDOUT with a non-zero exit (only a transport failure and the cap refusal go to stderr), so a caller keys off the exit code, never on stderr being empty — and otherwise parses stdout with a plain `json.loads` instead of guessing at interleaved `[INFO]` lines. It refuses, naming the cap, rather than printing a result that hit CEP's return limit: a readback over that size is PAGED, a fixed batch of rows per call, because full media paths make a whole-track read blow through 64 KB and surface as `Unterminated string … char 65534` inside the caller's parser. And `--timeout <ms>` reaches both the panel watchdog and the server's wait, which is what a long `exportAsMediaDirect` needs — the 45 s default is a watchdog, not a transport limit, and without it a perfectly good multi-GB export reports failure. **`es` is a WRITE path (the scripted export runs through it), so it runs the active-project guard like `replay` / `zoom` / `grade-layer` / `lay`, and `--no-guard` is the deliberate opt-out for a read that is not about a job** — ONE of the two is required and the command exits 2 without either, so the guard cannot be skipped by forgetting it exists (an unguarded ad-hoc script is exactly how 37 graphics landed on the wrong open project). `pes.es` passes `--no-guard` per call because a lane script guards ONCE at startup through `job_guard.require_job_project`.
- **The active project is checked before every write (2026-09-13).** Every lane writer acts on `app.project.activeSequence`, which is whatever project you last clicked, and Premiere keeps several projects open at once. With a job's v1 project active and its v2 project open behind it, `place-graphics.py --apply` for the v2 job laid all 37 v2 graphics over v1's timeline, splitting v1's own graphics underneath; the damage stayed in memory only because the run was interrupted before its save, and v1 came back by `app.project.closeDocument(0, 0)` (close without saving, no prompt) + `app.openDocument(path)` from its clean disk copy (the 16:01 save and every autosave were grepped for v2 paths first: zero). So `lanes/premiere/job_guard.py` runs in every writer (`place-graphics.py`, `place-sfx.py`, `place-music.py`, `audio-polish.py`, `review-frames.py`, the bridge's `replay`, `zoom` and `grade-layer`) before the first readback: the active project must be a `.prproj` under `projects/<job>/` or named after the job, else the script exits naming both projects and NOTHING is touched. The guard refuses, it never picks: making the right project active is the operator's click. Reading a wrong-project timeline is the same class of error as writing it (a readback of the wrong sequence reports drift that is not there), which is why `--verify` is guarded too. **The right project is not enough: the active SEQUENCE is checked after it (2026-09-22/23).** `app.project.path` named one job's project while `app.project.activeSequence` was another open project's timeline (09-22); one project holds a job's organic sequence beside its AD clone, and the active one switched from the AD to the organic between two grabs (09-23); and `activeSequence` is global, every `app.projects[j].activeSequence` returns the one focused timeline (live, 09-23). So `job_guard.require_job_project` and the bridge's own guard run THE SEQUENCE RULE on one shared readback with word-for-word refusals, S = the active sequence: (a) no S: refuse; (b) S is not one of the active project's own sequences: refuse, it belongs to another open project; (c) a requested name (`"sequence"` in the bridge opts, `es --sequence`, `require_job_project(es, job, sequence=)`, else env `VE_SEQUENCE`; opts beat env): S.name must equal it, else refuse naming both; (d) otherwise, when the project holds a sequence named exactly after the job folder and S is not it: refuse, naming `VE_SEQUENCE='<S.name>'`; (e) pass. Targeting any other cut (an AD clone) is deliberate, `VE_SEQUENCE='<job> AD' uv run lanes/premiere/place-graphics.py …`, never a name check hand-typed into each write (the 09-23 sessions did exactly that). On the bridge the rule covers `replay`, `zoom`, `grade-layer`, `lay`, `es --job`, and `frame` / `labels` / `clear-previews` given a `"job"`; a `"sequence"` without a `"job"` is refused. A refusal touches nothing (exit 2 on the bridge, 1 from a Python writer). **(b) is proved by the project FILE, not the sequenceID, in both guards:** a Save-As copy keeps EVERY sequenceID, so with the copy active and the original's timeline in front an ID match passed and a guarded grab exported the original (live, 09-23). `premiere-bridge.mjs` and `job_guard.py` (one GUARD_ES, character for character) also require S's `projectItem.treePath` to start with the active project's file name (`\<file>.prproj\[bins\]<seq>`), and refuse as ambiguous when another open project of the SAME file name holds S (a Finder copy, which Premiere opens beside the original without complaint): close the other copy. Regressions: `workflows/test_job_guard.py`, `workflows/test_premiere_bridge.py`.
- **Switch the active project with `app.projects[j].openSequence(seqID)`, never `app.openDocument(path)` of a project that is already open (2026-09-23).** On an already-open `.prproj`, `openDocument` returned false yet moved `app.project` to it while the focused timeline (`activeSequence`, QE's too) stayed the other project's: the exact state the sequence rule's (b) refuses, and the state in which the pre-rule guard let `place-music.py` lay a bed onto another project's timeline (reproduced live). Find `j` by matching `app.projects[j].path`, take the ID from `app.projects[j].sequences`, open it, then read the guard back before any write.
- **Project files live at `projects/<job>/premiere/<job>.prproj`, never Premiere's save-dialog default (the pruned Auto-Save folder).** A relocation leaves its Auto-Saves in the old folder; sweep them to `premiere/archive/` and verify the move via `app.project.path`, not the filesystem.
- **Drive the editor in the background; never front it.** `./workflows/window-grab.sh <App> <out.png>` captures a window's own buffer; most verification is a readback. The one exception is a PLANNED capture (`workflows/screen-record.sh`, a `capture` cell in the graphics plan): production footage of the timeline filling, not a verification frame, fronted for the take and said so in the report. Timeline colour labels are stamped from the project item at insert time and not scriptable per clip: label the item, then lay (a multi-section job replays one EDL per section, `setColorLabel(n)` on the item between replays, 2026-09-14); a section sharing its source file with a neighbour needs its own project item first, which is the colour-label rule's business (`premiere-pro` § colour labels). **The palette is readable, so a colour is picked by RGB distance, never by name and never with a throwaway clip:** `~/Documents/Adobe/Premiere Pro/26.0/Profile-*/Adobe Premiere Pro Prefs` carries `BE.Prefs.LabelNames.N` and `BE.Prefs.LabelColors.N`, the colour a BGR-packed int (`R = v & 255, G = v >> 8 & 255, B = v >> 16 & 255`; Iris = (0,75,103), Mango = (137,58,4), Green = (13,93,39), Magenta = (132,13,88), Yellow = (111,102,25), Purple = (97,0,183), Tan = (111,90,69)); it matched the earlier on-timeline measurements within the timeline's own tint. Launch = `./lanes/premiere/premiere-up.sh [project]` with the CEP autostart patch applied by `apply-autostart-patch.py` (re-run after any engine re-clone).
- **Never escalate a stuck quit to `kill` / `kill -9`.** Premiere logs any non-graceful exit as a CRASH: the next launch opens on an error-report modal that blocks the CEP panel, so bridge autostart silently fails, and post-kill timeline state comes back subtly wrong even after a `save_project` that returned success. Save through the bridge, quit gracefully (ExtendScript `app.quit()`, not an AppleEvent), then wait on the pid — and if it still will not quit, STOP and hand the app back to be quit by hand. `premiere-up.sh --restart` already refuses to escalate and exits with that instruction; keep it that way.
- **An ExtendScript edit does not dirty the project (Windows 26.5.1, 2026-09-27).** A marker made by script left no `*` in the title, and a quit (the bridge's `app.quit()` or a window close) raised no save dialog and dropped it; a QE edit (a razor) does dirty it and raises "Save changes to '<name>.prproj' before closing?". So every lane write saves itself, and a quit is never the save. On Windows `premiere-dismiss.sh` answers that dialog: Escape = Cancel (Premiere stays up), Return = Save.
- **Premiere under a password-locked screen (2026-09-02).** The headless bridge, EDL replay, audio polish, the grade layer, bridge `frame` renders and graphics placement all work; Premiere's UI does not (AX exposes no windows, menu presses and Cmd+Q / Cmd+O posted to it are ignored, `open -a <prproj>` is ignored by a running Premiere) and window grabs come back blank, so verify with bridge `frame` renders. An invisible native alert is diagnosed with `sample <pid>` (`UI_MessageBox::RunModal`) and dismissed with `lanes/premiere/premiere-dismiss.sh`; never kill Premiere for it.
- **yt-dlp downloads headed into Premiere must be H.264:** `-f "bv*[vcodec^=avc1]+ba[ext=m4a]/b[vcodec^=avc1]"` (Premiere cannot import AV1).
- **The bridge `frame` command now absolutizes a relative `out` against the CALLER's cwd, creates the parent folder, and fails if the PNG did not land (2026-09-08).** It used to hand the raw string to Premiere, whose cwd is its own app folder, and report success either way: 184 grabs landed nowhere on the first review-evidence pass (2026-09-07). `<out>.png` is the promised filename, so a trailing `.png` is stripped.
- **Converting a placed 1080 sequence to 4K is one ES pass (2026-09-07, your-job):** `seq.setSettings()` with videoFrameWidth/Height 3840/2160 takes effect on a populated timeline; every already-placed clip keeps Motion Scale 100 = its native pixels, so set 200 on the 1080 footage, the placeholder AND the GRADE adjustment layer (its Motion scales the layer's BOUNDS, which is exactly the coverage needed — verify by toggling the layer and reading the corners), 100 on true-4K sources (100.1 on a 3836-wide capture). Graphics are re-rendered at 4K as a new version and swapped by `place-graphics.py`, never scaled: a comp keeps its 1080 layout on a `scale(2)` stage inside a 3840x2160 root, NEVER `#root{zoom:2}` (the mechanism and the measured failure: `graphics-build` § render gotchas), 5–55 s per render.
- **A timeline change is bracketed OFFLINE from the auto-saves (2026-09-10, your-job).** A `.prproj` is gzip XML; `<Start>`/`<End>` ticks ÷ 8,475,667,200 = frames at 29.97 (254016000000 ticks/s × 1001/30000), so diffing those values between two auto-saves says WHEN a cut moved without opening anything. A 10-frame drag of a V1 clip (source in/out unchanged, the previous clip's tail overwritten, a 10-frame hole left behind) landed between two auto-saves while the only commands running were file reads, i.e. from the Premiere UI; the next placer save then persisted it, because `--verify` reads the graphics rows only, never V1. The repair primitives: `trackItem.move(seconds)` is a RELATIVE shift (the vendor passes a plain number) — **and on script-laid clips the linked A1 clip did NOT follow it (astra final-thoughts, 2026-09-14: 20 V1 clips closed a ripple gap, their 20 A1 clips stayed 4.96 s late until moved separately), so move the audio track's items by the same delta and read V1/A1 start, end and inPoint back PAIRWISE before saving;** `clip.end = t` extends a clip (speed stays 1) but the DOM's `outPoint` reads STALE afterwards, so the proof is a voice-only bounce over in/out (`exportAsMediaDirect(wav, Wave48mono24.epr, 1)`) cross-correlated against the raw source, never the readback — **and the stale value outlives the session that caused it: a LATER read of that timeline sees an `outPoint` shorter than the clip and it looks exactly like a hand trim (your-job, 2026-09-21: an in-place +21-frame extend from the day before was logged as the creator cutting a line back out, a wrong EDL was written from it, and the re-derived transcript ran 0.876 s early for everything after that clip, mis-syncing six graphics). When an EDL is derived from a live V1 readback, source-out is `inPoint + (end − start)`, never `outPoint`; any clip where the two disagree by more than a frame is reported as STALE-OUTPOINT, not as an edit, and the derived EDL's total must equal the sequence's length** (`lanes/premiere/live-edl.py` is that reader: it prints STALE-OUTPOINT, checks the total, refuses V1 media no EDL names, and writes only with `--write`, backup first; `--edl` points it at another sequence's EDL; `premiere-bridge.mjs diff-edl` derives the out the same way; proven live 2026-09-23, where the stale outPoint also read LONG after an in-place trim and survived save, close and reopen); `seq.clearInPoint` does not exist, `setInPoint(-400000)` restores the unset state.
- **ExtendScript mutations do NOT enter Premiere's undo stack (your-job, 2026-09-19).** Five `app.executeCommand` undos and the MCP `undo` / `multiple_undo` tools all returned success and changed nothing after a scripted wipe, so there is no recovery inside the app: the SAVED `.prproj` is the only rollback. `save_project` BEFORE any write that touches clips which already exist (a re-lay, a sweep, a remove, a ripple), and count the affected track's clips before and after.
- **`clip.disabled = true` is how a clip is muted from a script.** `TrackItem.setDisabled`, QE's `setEnabled` and the vendor `batch_enable_disable` tool all fail or act on the wrong set (it reported changing 596 clips); read the flag back as `clip.disabled`.
- **Two sequences are proven identical with `uv run lanes/premiere/timeline-dump.py projects/<job> --diff "<organic>" "<AD>" --until <CTA s>`, never a hand dump (2026-09-23).** A one-shot dump of a graded sequence hits the CEP return cap (350840 chars: the Lumetri blob), and a hand pipeline swallowed that error into an empty `dump.json`. The tool reads both sequences by name without activating them (either may be active, no `VE_SEQUENCE`), pages 40 clips then 40 transitions per call, hashes every component property inside Premiere, and under `--until` hashes the keyframes only as they play before the CTA, so a bed fade that moved with the AD's end is not a difference. It prints only what differs (exit 1); a refused or failed read is exit 2, never 1. Proven live, your-job's own organic and AD included (about 11 s a run). It compares media PATHS, so an AD that carries its own pixel-identical caption render never reads IDENTICAL: that one stays a pixel proof.
- **timeline-dump.py quantizes only NON-INTEGER numbers, and walks arrays by hand (2026-09-23).** A script-copied Level key came back one float32 ulp off after save and reopen (proven live), so fractions hash at 5 significant digits. A colour param's getValue() is a 64-bit PACKED integer (White Balance 255,192,192,192 = 18374897589125431000), which 5 digits would collapse to its alpha, so integers hash verbatim. Premiere's ExtendScript JSON.stringify IGNORES a replacer function, so ES code must never rely on one: walk the value first. The node mock in `workflows/test_live_edl.py` ignores replacers too.

## Step 2 · replay

- **Never render the flat cut on this lane; the audio polish is step 3, right after the replay.** `RENDER=0 splice.sh` → `premiere-bridge.mjs replay` (time-to-timeline is the metric, transcription the only slow step). No gain, no level-matching during the cut. Then `uv run lanes/premiere/audio-polish.py projects/<job> --apply` (measured gain + Hard Limiter −6 dBFS as clip effects on every A1 clip, readback-verified); a re-replay discards clip effects, re-apply before saving. Owner: `premiere-pro` skill § Step 3.
- **OBS recordings carry two identical AAC tracks and Premiere silently refuses the file.** Remux losslessly first (`ffmpeg -i raw.mp4 -map 0:v:0 -map 0:a:0 -c copy -movflags +faststart out.mp4`); duration is unchanged so an EDL still applies. Clip deletion IS scriptable: `moveBin` into a fresh bin, then `deleteBin()`.
- **A frame-range sweep that removes clips must name its TRACKS (your-job, 2026-09-19).** Moving a section to the front of a sequence with a remove-then-shift script swept every track over the vacated range and silently took two SFX with it; the loss only surfaced when the creator noticed a missing whoosh. Sweep only the tracks the move owns, and run `place-sfx.py --diff` then `--verify` afterwards; zero missing, extra or drifting cues is the gate (the step-6 owner is [`presets/youtube/default/sfx.md`](../../presets/youtube/default/sfx.md) § Definition of done).
- **An audio `overwriteClip` from a SUBCLIP ignores the out-point and lays the WHOLE media, wiping every later clip on that track (your-job, 2026-09-19).** The end-trim afterwards hides it: the clip looks right and three later clips are simply gone. Lay audio rows in ASCENDING time order so each lay re-creates the next, read the laid LENGTH back before trimming, and count the track's clips before and after.
- **A laid clip's colour cannot be READ back on this lane, so the confirmation is a window grab (your-job, 2026-09-19).** `TrackItem` exposes no `getColorLabel` and every item-side answer (the MCP's `select_clips_by_color` included) reports the PROJECT ITEM's current label, not the colour the clip displays — which is how an item-name audit "proved" five clean colour runs on a timeline that was visibly wrong. `workflows/window-grab.sh "Adobe Premiere" out.png` grabs the window in place (Retina, so the capture is 2x the point size) and a crop of the V1/A1 strip shows the runs at a glance. The rule the check serves is the owner's: `premiere-pro` § colour labels.
- **A HARD-BOUNDARY subclip is how you lay one audio row safely.** `createSubClip(name, in, out, 1, 0, 1)` lays exactly its own length, so re-laying a single A1 clip no longer wipes the rest of the track (the plain-subclip runaway above); it also carries its own colour label, which is how a mis-coloured clip is fixed in place. Its in-point is SUBCLIP-relative, so any EDL derivation must map it back to source time rather than reading `inPoint`, and a subclip laid over a dialogue row is skipped in an A1 cross-check by name rather than trusted as source time. **Where a lay subclip starts in its media is its metadata, never `getInPoint()` (live, 2026-09-23).** On the subclip `lay` makes, `ProjectItem.getInPoint()` reads 0 (so do `getInPoint(1)` and `getInPoint(4)`) and `getOutPoint()` the subclip-relative length; the start is the `<premierePrivateProjectMetaData:offset>` inside `Column.Intrinsic.VideoInPoint` in `getProjectMetadata()` (it read 508565433600, the lay's 2.0021 s in-point to the tick; SubclipStart shows it as a timecode), and the track clip's `inPoint` counts from that offset. On media that carries a start timecode the offset includes it (a master of a file stamped 01:00:10:00 read 917914757760000, its subclip that plus the in-point), so subtract the master's own offset; a Source Monitor mark on a master moves `getInPoint()` and leaves the offset at 0. `live-edl.py` refuses a lay subclip rather than map it.
- **A project item's VideoInPoint offset is on the media's TIMECODE clock, not its media clock (live, 2026-09-23).** On a master it IS the file's start timecode (01:00:10:00 at 23.976 read 86640 frames). On a `lay` subclip it is the start timecode plus the subclip's start. Any tool that maps a lay row onto source time takes the file's start timecode off first (ffprobe `timecode`, `workflows/grey-source.py` probe `tc_frames`, in ticks on the source grid; drop-frame timecode counts SMPTE-DF real frames, proven at 29.97 DF). Only media with no timecode has a master offset of 0. `frame-proof.py` does this, and it reports an offset below the timecode as unmeasured (exit 2), never as a verdict. Its one blind spot: an item re-timecoded in Premiere (Modify > Timecode) to a start AFTER the file's own reads as a subclip start and FAILs correctly placed rows; undo the override before proving.
- **A head trim is `start =` AND an in-point written in TICKS; a float-seconds in-point can render the frame before while every readback says it is right (2026-09-22, proven on program grabs of a grey-coded source).** `clip.start = t` moves the head and leaves the in-point where it was, so the picture slides a frame; the in-point has to be moved by the same delta. Written as `ti.seconds = inPoint.seconds + delta`, it landed ONE TICK under frame 767: Premiere floored it into frame 766, and `.seconds` readbacks, a 0.002 s tolerance and a frame-rounded readback all reported 767. Do the arithmetic on `Number(x.ticks)`, write `ti.ticks`, compare ticks exactly, and prove a trim on a program grab (`lanes/premiere/frame-proof.py --clear-previews`). `premiere-bridge.mjs lay` does this for the clip it straddles, and `place-blur.py` for each blur layer's in-point (V1's mapping summed in ticks, written as `ti.ticks`, the readback compared tick-exact; proven live 2026-09-23); `trackItem.remove(false, false)` on a video-only remnant leaves the linked A1 clip alone. **A `trackItem.inPoint` written in ticks is stored VERBATIM on a mixed-rate clip too:** on 24 fps and 30 fps sources on a 23.976 sequence the saved in-points sit on neither the source nor the sequence grid (your-job's `.prproj` decoded, and program grabs on a grey-coded source, 2026-09-23). Only `overwriteClip` / `setInPoint` floor to the grids; the trackItem setter does not.
- **An alternate camera angle is lip-sync-measured BEFORE its first clip is laid (2026-09-19).** `uv run workflows/lip-sync.py <cam> --audio <mic-source> --mouth-crop <w:h:x:y>` (the crop is measured off one frame of the cam — `rough-cut` § Gotchas; without it the tool exits 2 UNMEASURED rather than answering); on FAIL each camera clip's source in-point slips LATER by its own lag AT ITS OWN SOURCE TIME — the lag drifts across a long take, so one number for the whole angle is wrong — with the clip's timeline start and end unchanged, and the applied lag is stamped into the clip name (`CAM +Nf`) so re-running the pass is idempotent. Prove it on a timeline export, never the readback. Owner: `rough-cut` § Gotchas.
- **Every clip laid after the first replay carries its SECTION's colour (2026-09-19).** Owner: `premiere-pro` § Colour labels.
- **NEVER `overwriteClip` an AV project item onto an AUDIO track (your-job CAM CUTS, 2026-09-19).** Doing it to re-lay three dialogue rows wiped A1 from that point to the END of the sequence (39 clips) and laid the items' VIDEO halves at ~53 minutes, stretching the sequence to 3205 s; damage like this is not undoable (next bullet), so it had to be rebuilt from the EDL. An audio track takes an AUDIO-ONLY subclip and nothing else, and it is HARD-boundary like every other lay: `createSubClip(name, in, out, 1, 0, 1)` — arg 4 is `hasHardBoundaries` and a 0 there re-creates the soft-subclip runaway above (the one that lays the WHOLE media and wipes the rest of the track). The same call on V1 rewrites A1 underneath it (a frame early, chain gone), so a video-only subclip is the rule there too. Which is why laying a row onto a track that ALREADY holds clips goes through `node lanes/premiere/premiere-bridge.mjs lay '{"job":"projects/<job>","item":"<item name>","track":"A1","in":<s>,"out":<s>,"at":<s>}'` (`job` is REQUIRED — it is what runs the active-project guard): it derives the subclip flags from the track's KIND rather than the caller (so an AV item cannot reach an audio track at all), lays a hard-boundary subclip, and aborts naming both numbers when the track's clip count falls by more than the rows it replaced — the check that would have caught the 39-clip wipe in the same second. Never a hand `overwriteClip` onto a populated track.
- **An `overwriteClip` whose source out-point overshoots by a hair lays ONE FRAME TOO MANY and trims the head off the next clip (your-job, 2026-09-19).** Setting the new clip's `end` back then leaves a one-frame hole, black on V1 and silent on A1, and the neighbour has silently lost a frame of its in-point. Set the out-point just UNDER the wanted length (the clip's own `end` is what fixes the tail), and audit after placing: every clip's in-point against the EDL, plus a gap scan on V1 AND A1.
- **Never build clip copies by razoring and then `trackItem.move()`-ing the pieces to earlier times (your-job CAM CUTS, 2026-09-19).** QE keeps a track's items in CREATION order, so moved clips sit out of order, QE reports the span they cover as one Empty, a razor on that track stops taking, and the renderer intermittently skips them: adjustment-layer grades flickered on and off and did not render. Laying an effect-carrying clip (a GRADE with its Look) over several windows is therefore ONE clip razored in place, never moved copies — the procedure and its proof: [`premiere-grading.md`](premiere-grading.md) § 1.
- **A scripted ripple (`trackItem.move()` on hundreds of clips) leaves STALE render-cache frames behind (your-job CAM CUTS, 2026-09-19).** The Program monitor and `exportFrame` kept showing an outro text animation 7 s before its clip, where every track, DOM and QE, was empty; muting any track made it vanish. After any scripted move, clear the sequence's render files: `node lanes/premiere/premiere-bridge.mjs clear-previews '{"job":"projects/<job>"}'` (pass the job, or the active-project guard does not run and the previews cleared are whichever project is in front) runs the QE call `qe.project.getActiveSequence().deletePreviewFiles('00:00:00:00', '<end tc>')` over the whole sequence (the one-argument form throws "Not Enough Parameters"; the end timecode is the sequence end's ceiling plus one frame, built with the same nominal-fps helper the `frame` command uses; proven live 2026-09-23: a phantom V2 frame left by a `c.move(5)` under a stale green bar was gone after it, the `.PRV` folder emptied). QE reads and makes render bars headlessly: `qe.project.getActiveSequence().getGreenBarTimes()` / `getRedBarTimes()` / `getYellowBarTimes()` (QETime.secs) read them, and `renderAll()` renders previews.
